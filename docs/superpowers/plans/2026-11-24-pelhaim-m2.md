# pelhaim M2 (Launch mode, planning, pelhaim as orchestrator) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner types a goal, pelhaim drafts a plan with a launched `claude -p` planner, and the owner reviews it on the board or in `$EDITOR` as TOML and approves it. pelhaim then runs one `claude -p` or `codex exec` train per ready step. Each train works in its own worktree on its own branch, stacked on its predecessor's branch. A step is done when the agent declares it complete and pelhaim's own checks pass. Questions, permission requests, sign-offs, merge conflicts and push/PR approvals come back as alerts, and every decision is logged. pelhaim never merges, never touches `main`, and never pushes without an approved alert.

**Architecture:** Everything stays in M1's shape. The pure `Engine` gains plans, plan stations, launched trains, the definition-of-done state machine and the git alerts. It asks for side effects through a new `Effect::Job(Job)` and learns results through a new `Input::Orch(OrchEvent)`. A new `orchestrator` executor in the binary crate runs those jobs: git worktrees and merges, check commands, launched CLI processes, the planner, the take-over terminal and the plan editor. Launch adapters in `pelhaim-adapters::launch` build exact argv, parse the CLIs' JSON streams into M1's `Event`s plus completion signals, and own the child processes. A hidden `pelhaim mcp-step` subcommand serves the `step_complete` tool over stdio MCP.

**Tech Stack:** M1's stack (Rust 1.100.0, edition 2024, tokio, serde/serde_json/toml, rusqlite bundled, chrono, clap, winit, wgpu, accesskit). New: `uuid` (v4, Claude session ids), tokio `process` in `pelhaim-adapters`. External CLIs: `claude` (Claude Code; 2.1.332 on this machine 2026-11-24), `codex` (codex-cli 0.158.0), `git` (2.53.0), `gh` (2.89.0).

**Spec:** `docs/superpowers/specs/2026-11-23-pelhaim-design.md`. §5.1, §5.2 and §16 override the rest. M2 scope is §13 "M2", with §7.5, §7.7–§7.9, §8.2, §8.4, §8.5, §9.4, §9.6, §10 and §10.1. Also two **owner changes of 2026-11-24** that are not yet in the spec (listed under Global Constraints). Build on M1 as merged from `feat/m1-observe` (PR #1), plus the M1 follow-up that implements those two changes.

## Global Constraints

- Every M1 Global Constraint still holds: the PATH note (`export PATH="$HOME/.cargo/bin:$PATH"`), the gate (`cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace`) before every commit, no `unsafe`, `cargo add` with `Cargo.lock` committed, load-bearing comments only, and a `CHANGELOG.md` line `- YYYY-MM-DD: …` under `## Unreleased` for every user-visible change. Also: no transcript text persisted or logged, synthetic fixtures only, `pelhaim-core` does no IO and never reads the clock, and tests never touch the real `~/.claude`, `~/.codex`, `~/.config/pelhaim`, `~/Developer/DECISION-LOG.md` or any real repo.
- **Branch:** work on `feat/m2-launch`, created from `main` once PR #1 and the M1 owner-change follow-up are merged. Never commit to `main`. Never push and never open a PR: that is the owner's call (`/commitandpush`).
- **Owner change A (2026-11-24): no train for the orchestrator.** DISPATCH is a slim header strip with an agent count. An orchestrator's subagents appear only on their own project lines, and its questions still raise alerts. pelhaim-as-orchestrator follows the same rule: the planner run and the scheduler get **no train**. They are counted on the DISPATCH strip, and their alerts (PlanReview, planner failure) carry `train: None` and `line: LineKey::Dispatch`.
- **Owner change B (2026-11-24): stations come only from explicit `pelhaim-milestone: <name>` marker lines.** Prompts and tool calls never create them. Visible stations are capped (about 5), and older ones fold. In M2 **a plan's steps are its milestones**: the engine creates one station per plan step from the plan itself. Every launch prompt carries the marker line `pelhaim-milestone: <step title>` as its second line, so an observer of the session's JSONL (including after take-over) derives the same station.
- **Owner change C (2026-11-24): stations carry arrival times.**
  - The marker takes an optional estimate: `pelhaim-milestone: <name> ~20m`.
  - pelhaim learns a correction factor (the median of actual/estimate, per project, with a global fallback) and shows clock arrivals, which turn amber when overdue.
  - In M2:
    - every plan step carries `estimate_hours` (agent hours, `> 0` and `<= 40`), written by the planner;
    - every spawn prompt's marker line carries that estimate;
    - the learned factor drives the plan view's ETAs and each train's projected arrival at its plan's final station;
    - finished plan stations feed the factor, with actual = from the station going `Active` to the agent declaring complete. Checks and sign-off waits are excluded.
- **Depends on the M1 follow-up landing first:** Tasks 5, 6, 7, 14, 15, 16 and 17 touch the DISPATCH strip, the station model, the milestone parser/formatter or the ETA model that the follow-up introduces. Their implementers must read the merged follow-up code and use its real names. This plan uses three placeholder names for what the follow-up exports:
  - `parse_milestone` / `format_milestone(name, estimate)`: the `pelhaim-milestone:` parser and formatter, including the `~20m` estimate syntax;
  - `EtaModel::factor(project) -> f64` and `EtaModel::record(project, estimate, actual)`: the learned correction factor;
  - the board's overdue-amber rule.

  Task 14's prompt also depends on `format_milestone`. Tasks 1–4 and 9–13 do not use its code directly. Tasks 8, 11 and 12 still build on Task 5's types, so they run after Task 5. Task 1, the spike, can start now.
- **Fixed rules, never configurable (§7.8, §10.1, §5.1):**
  - pelhaim never runs `git merge` into, `git commit` on, or `git push` to the project's base branch;
  - pelhaim never runs `gh pr merge`;
  - `git push` and `gh pr create` run only from an answered `GitApproval` alert;
  - steps flagged `decision`, `merge`, `prod` or `security`, and steps with a `Manual` check, always stop for sign-off;
  - no plan departs before the owner approves it.
- **Auto mode is the default (§5.2, §10.1):**
  - `[approval]` defaults: `read_only`, `worktree_write`, `worktree_exec` and `git_train_branch` are `allow`; `outside_worktree`, `network`, `secrets` and `destructive` are `ask`.
  - `--dangerously-skip-permissions`, `bypassPermissions` and `--dangerously-bypass-approvals-and-sandbox` are never passed. M2 exposes no config key for them (§10 permits leaving them unexposed).
- **CLI flags:** only flags verified with `--help` on 2026-11-24 (Task 1, step 1), or confirmed in the Task 1 findings, may appear in spawn argv. If a finding contradicts this plan, the Task 1 findings doc lists the amendment and execution stops for owner review before Task 12.
- **Prompt lines (exact):**
  - Line 1 of every launch prompt is `pelhaim-project: <slug>`.
  - Line 2 is `format_milestone(<step title>, <estimate_hours>)`, e.g. `pelhaim-milestone: Migrate the schema ~2h` (owner changes B and C).
  - The planner's prompt line 1 is `pelhaim-project: dispatch`.
- **Branch and path names (§7.8):**
  - branch `pelhaim/<project-slug>/<step-id>-<train#>`, using `[git].branch_prefix` (default `"pelhaim/"`);
  - worktree `<worktree_root>/<project-slug>/<step-id>-<train#>`, with `worktree_root` defaulting to `~/.local/share/pelhaim/worktrees`;
  - a root step's base is the project's `base_branch` (default `"main"`).
- `max_check_attempts = 3`, check timeout `20m`, and check output kept at most 64 KiB (the tail) per check. `max_concurrent = 4`.
- Launched CLIs inherit pelhaim's environment, because they need their own auth. Check commands get a scrubbed environment from an allowlist: `PATH HOME USER LOGNAME SHELL LANG TERM TMPDIR CARGO_HOME RUSTUP_HOME`, every `LC_*`, and the project's `check_env` list.
- Every child pelhaim spawns (CLI, check, git, gh, terminal opener) has `kill_on_drop(true)` and runs in its own process group. Quitting pelhaim kills launched trains and checks. A take-over terminal is the exception: it is spawned detached, on purpose.

## Review Focus

1. **pelhaim quits or crashes while trains run, then restarts.** The owner expects:
   - no orphaned `claude`/`codex` processes;
   - stations that were Active or Checking come back as Failed("interrupted by restart") with `[Retry station]`, and Retry resumes the same session in the same worktree;
   - no second worktree or branch for the same station;
   - approved plans, Done stations and sign-offs survive.

   Pinned in Task 8 (`restart_marks_active_stations_interrupted`) and Task 14 (`dropping_orchestrator_kills_children`).
2. **A worktree path or branch already exists, or the project root is dirty or not a git repo.** Causes include a re-run of a plan, a leftover from a failed run, or the same train number in the same minute. The owner expects pelhaim never to reuse, force or overwrite anything. The station shows Failed with a `Failure` alert naming the reason, and Retry picks the next free train number. Pinned in Task 9 (`existing_branch_is_refused_not_forced`, `root_not_a_repo_fails_cleanly`) and Task 5 (`retry_after_worktree_failure_uses_next_number`).
3. **Agent text that looks like a completion signal but isn't:**
   - the JSON inside a code fence;
   - the JSON mid-message, not on the last line;
   - a `step_complete` naming another station;
   - two signals in one message;
   - malformed JSON;
   - an MCP `step_complete` call with an unknown `station_id`.

   The owner expects only an exact last-line match, or the MCP tool call, for the train's own station, and anything else leaves the station Active. Pinned in Task 11 (`signal_rejects_lookalikes`) and Task 6 (`step_complete_for_other_station_is_ignored`).
4. **Stale or repeated owner actions:**
   - approving plan revision 1 after an edit made revision 2;
   - signing off a station that was rejected and is running again;
   - approving the same `GitApproval` from the Mac and the phone;
   - double-pressing `Enter`.

   The owner expects the first answer to win, a superseded revision to be refused, and push/PR to run exactly once. Pinned in Task 5 (`approving_superseded_revision_is_refused`) and Task 7 (`git_approval_runs_once`, `signoff_after_reject_is_refused`).
5. **The project's git setup differs from the happy path:**
   - the base branch is `master`;
   - there is no `origin` remote;
   - `gh` is not authenticated;
   - push is rejected.

   The owner expects the base to come from `[[project]].base_branch`, a push or PR failure to raise one `Failure` alert with the first stderr line and no secrets, the `GitApproval` to stay in the tray for a retry, and no retry loop. Pinned in Task 9 (`push_without_origin_reports_error`) and Task 7 (`push_failure_keeps_approval_retryable`).

Keyword matching rules:
- matching is case-insensitive, on whole words (ASCII word boundaries), over `title + " " + detail`;
- multi-word keywords match their words in sequence;
- `keyword_override = true` suppresses keyword errors only, never `DesignField` or `SecurityField`.

Mapping:
- `design` → `Decision`;
- `security` → `Security`;
- a design keyword → `Decision`;
- a security keyword → `Security`;
- a merge keyword → `Merge`;
- a prod keyword → `Prod`.

Layout (§7.5):
- columns = the longest path from a root, counted in edges;
- chains = greedy path cover: take the longest remaining path (ties broken by the earliest step in plan order), remove it, repeat;
- skipped steps are left out.

Behaviour:
- **Planning:**
  - `PlanGoal` checks that the project has a `ProjectLaunch` entry; if not, it raises a `Failure` "launch is not set up for <slug>: add its path". Otherwise it emits `Job::Plan` with a fresh request id.
  - No train is created (owner change A). The DISPATCH strip's agent count includes running planner requests, so expose `Snapshot.dispatch_agents: u32` = planner requests in flight + the follow-up's own count.
- **Draft review:**
  - `PlanDrafted` → `Plan { status: Draft, revision: 1 }`, then `validate`.
  - Raise `PlanReview` with `train: None`, `line: Dispatch`, `answerable: true`, and `errors` from `validate` (Display strings).
  - Draft stations are drawn on the project line with status `Pending` (Task 15 draws them dim). Tracks are `layout` chains, one station per non-skipped step, titled with `step.title`.
- **Answering `PlanReview` (`Choice::Options`):**
  - `[0]` approve: refused with `InvalidChoice` while `errors` is non-empty, or when the alert's `revision` ≠ the plan's current revision.
  - `[1]` discard: plan Abandoned, stations removed.
  - `Choice::Text(feedback)` → `RevisePlan`.
  - Approval sets `Approved`, writes a `Decision` row automatically (§8.5 rule 2/4): title `Plan approved: <goal head>`, why `"<n> steps, revision <r>"`, `who: Owner`, the answer's origin, `source_alert` = the alert. It persists `OwnerEvent::DecisionLogged`, without exporting.
- **Edits:**
  - `EditPlan` → `Job::EditPlan(plan)`.
  - `PlanEdited` with `revision` = current → revision + 1. It expires the old `PlanReview` and raises a new one for the new revision.
  - `PlanEditInvalid` → a `Failure` alert listing `line N: message` rows; the plan is unchanged.
- **Scheduling, after every fold:**
  - while fewer than `max_concurrent` launched trains are Working/Checking/Waiting, take the next station (plan order) whose status is `Pending` and whose `effective_deps` are all `Done` or `Skipped`;
  - mark it `Ready`, create its `Train` (state `Idle`, `train_number(now)` with M1's collision rule, `tag: Tagged(slug)`, `parent: None`), and emit `Job::PrepareWorktree`;
  - base = the base branch for a root step, else the first effective dependency's branch; `merge` = the other dependencies' branches;
  - an `AwaitingSignoff` dependency does not count as Done (§7.5).
- `WorktreeReady` → train `worktree` set, station `Active`, `Job::Launch` (§8.2.3).
- `WorktreeFailed` → station `Failed`, train `Failed(reason)`, and a `Failure` alert with `[Retry station]`. `RetryStation` resets the station to `Pending` with a new train number (the next free minute).
- `LaunchOne` = a one-step plan:
  - step id `task`, title = the first 40 chars of the prompt, `detail` = the prompt;
  - acceptance is the project's default check;
  - `Approved` at once, with a decision row `Launched one train: <title>`, why `pelhaim launch`.
- A plan becomes `Done` when every non-skipped station is `Done`.
- **ETAs (owner change C):**
  - each plan station carries `eta: Option<Ts>` in the snapshot. While the plan is a draft, it is `now + projected_finish(...)` using `EtaModel::factor(project)`. Once the plan is approved it counts from the plan's approval time, and Done steps use their actual finish.
  - each launched train carries `projected_arrival: Option<Ts>`, its plan's final-station ETA;
  - an Active station's own arrival is `active_since + estimate_hours × factor`, so M1's overdue-amber rule applies to it unchanged;
  - the engine holds the learned model: `EngineConfig`/`RestoredState` carry the follow-up's `EtaModel` state, and nothing here re-implements the median.

- Every invocation is argv (never `sh -c`) with `-C <root>` or the worktree as cwd, `kill_on_drop`, and `GIT_TERMINAL_PROMPT=0`.
