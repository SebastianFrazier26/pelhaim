# pelhaim M2 (Launch mode, planning, pelhaim as orchestrator) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner types a goal, pelhaim drafts a plan with a launched `claude -p` planner, and the owner reviews it on the board or in `$EDITOR` as TOML and approves it. pelhaim then runs one `claude -p` or `codex exec` train per ready step. Each train works in its own worktree on its own branch, stacked on its predecessor's branch. A step is done when the agent declares it complete and pelhaim's own checks pass. Questions, permission requests, sign-offs, merge conflicts and push/PR approvals come back as alerts, and every decision is logged. pelhaim never merges, never touches the base branch, and never pushes without an approved alert.

**Architecture:** Everything stays in M1's shape:

- **Engine (pure):** the `Engine` gains plans, planned stations on each project's single line, launched agents, the definition-of-done state machine and the git alerts. It asks for side effects through `Effect::Job(Job)` and learns their results through `Input::Orch(OrchEvent)`.
- **Orchestrator:** a new executor in the binary crate runs the jobs: git worktrees and merges, check commands, launched CLI processes, the planner, the take-over terminal and the plan editor.
- **Launch adapters:** `pelhaim-adapters::launch` builds exact argv, parses the CLIs' JSON streams into M1's `Event`s plus completion signals, and owns the child processes.
- **MCP server:** a hidden `pelhaim mcp-step` subcommand serves the `step_complete` tool over stdio MCP.

**Tech Stack:**

- M1's stack: Rust 1.100.0, edition 2024, tokio, serde/serde_json/toml, rusqlite (bundled), chrono, clap, winit, wgpu, accesskit.
- New: `uuid` (v4, for Claude session ids) and tokio `process` in `pelhaim-adapters`.
- External CLIs, as checked on this machine 2026-11-24: `claude` 2.1.332, `codex` (codex-cli) 0.158.0, `git` 2.53.0, `gh` 2.89.0.

**Spec:** `docs/superpowers/specs/2026-11-23-pelhaim-design.md`.

### Owner decisions M2 must follow

- **A. No train for the orchestrator** (§5.3.1).
  - When pelhaim orchestrates, the planner and the scheduler get no train.
  - The DISPATCH strip's `running` count adds pelhaim's **planners in flight only** (owner, F3). Launched agents appear only on their project lines.
  - Planner alerts (PlanReview, planner failure) carry `train: None, line: LineKey::Dispatch`.
- **B. Stations come only from markers** (§5.3.2). A plan's steps are its milestones.
  - An approved plan's steps become planned stations on the project's **single line**, created by the engine from the plan itself and shown **at once** with their ETAs, before any agent starts (owner F6 as amended by F).
  - Every launch prompt carries `format_milestone(title, estimate)` as line 2, so an observer derives the same name.
  - For plan agents, `Event::Milestone` never creates or closes a station (F8).
- **C. Arrival times** (§5.3.3, §7.10).
  - Every planner- or TOML-written step carries `estimate_hours` (agent hours, `> 0` and `<= 40`).
  - The marker carries `estimate_secs_from_hours(h)`.
  - The factor `correction_factor(&timings, Some(slug))` drives every plan station's projected clock and each train's projected arrival at its plan's final station.
  - A Done plan station records one `StationTiming` with key `plan:<plan_id>/<step_id>`. Its actual time is the sum of the station's Active intervals; Checking and AwaitingSignoff time are excluded (F31).
- **D. Repo auto-registration** (§7.7, 2026-11-24).
  - Launched trains run in linked worktrees of the configured project repo, so anything observe sees from them resolves to that project's line by `Repo(slug)`, even untagged. This covers subagents, a taken-over session, and a session rediscovered after a restart.
  - M2 relies on this: observe stays the only source of subagent trains (F14), and launch prompts still write the `pelhaim-project:` tag line, which wins first anyway.
  - Launch needs a **configured** `[[project]]` with `path` (`Config::launch_project`). An auto-created line, with no config entry, cannot launch or plan, and says how to add one.
- **E. Derived sign-off flags are added automatically, never rejected** (owner, F28).
  - Flags derived from the step fields and the keyword lists are added to `signoff` when a plan is drafted, edited or launched.
  - Plan review marks them as derived.
  - `keyword_override = true` suppresses keyword-derived additions for that step, never field-derived ones.

- **F. One train per project line** (owner, 2026-11-24; the M1/main board change). This overrides F6 as written.
  - Each project line has exactly one train and one track.
  - All the agents in a project, launched or observed, fold into that train.
  - The train's state is aggregated: waiting-on-you beats failed, which beats working, which beats idle, which beats done.
  - All milestones become stations on the one line, in time order.
  - Forks are no longer drawn as separate tracks.
  - Each line has its own base colour. State shows on the train tag and the stations, never by recolouring the line.
  - Lines have real-train-line geometry.
  - **For M2:**
    - parallel plan chains still run as separate agents, each with its own worktree, but the board shows one train and one line;
    - planned stations are ordered on the line by projected ETA, with ties broken by layout column and then plan order;
    - per-agent state (state, worktree, session, handle) stays in the engine, one internal `Train` record per agent, which the board change aggregates.
  - The board change's real names (aggregate state, line train, station ordering, line colour) are not known yet. Tasks 5, 6, 7, 8, 15, 16 and 17 must read the landed code and use its names. Where this plan writes `line_train` or `aggregate_state`, it means whatever that change exports.
  - **Tasks that depend on the board change landing on main first:** 5, 6, 7, 8, 15, 16 and 17. Tasks 1–4 and 9–14 do not.

### Fixed rules, never configurable (§7.8, §10.1, §5.1)

- pelhaim never runs `git merge` into, `git commit` on, or `git push` to the project's `base_branch`.
- It never runs `gh pr merge`.
- `git push` and `gh pr create` run only from an answered `GitApproval`.
- Steps flagged `decision`, `merge`, `prod` or `security`, and steps with a `Manual` check, always stop for sign-off.
- No plan departs before the owner approves it.

### Auto mode is the default (§5.2, §10.1)

- `[approval]` defaults to `allow` for `read_only`, `worktree_write`, `worktree_exec` and `git_train_branch`, and to `ask` for `outside_worktree`, `network`, `secrets` and `destructive`.
- `--dangerously-skip-permissions`, `bypassPermissions` and `--dangerously-bypass-approvals-and-sandbox` are never passed. M2 has no config key for them.

### CLI flags

- Only flags confirmed with `--help` on 2026-11-24, or in the Task 1 findings, may appear in spawn argv.
- If a finding contradicts this plan, the findings doc lists the amendment and execution stops for owner review before Task 12.

### Prompt lines (exact)

- Line 1 of a launch prompt is `pelhaim-project: <slug>`.
- Line 2 is `format_milestone(&step.title, step.estimate_hours.map(estimate_secs_from_hours))`, for example `pelhaim-milestone: Migrate the schema ~2h`.
- The planner prompt's line 1 is `pelhaim-project: dispatch`.

### Names and defaults

- **Branches and worktrees (§7.8):**
  - branch: `<branch_prefix><project-slug>/<step-id>-<train#>`, with `branch_prefix` defaulting to `"pelhaim/"`;
  - worktree: `<worktree_root>/<project-slug>/<step-id>-<train#>`;
  - `worktree_root` defaults to `<data_dir>/worktrees`, which is `~/.local/share/pelhaim/worktrees` unless `PELHAIM_DATA_DIR` is set (F42);
  - a root step's base is `base_branch` (default `"main"`).
- **Checks:** `max_check_attempts = 3`, a check timeout of `20m`, and at most 64 KiB of output kept per check (the tail).
- **Concurrency:** `max_concurrent = 4`, counted as plan stations in `Ready | Active | Checking` (F15).

### Child processes and environment

- **Environment:** launched CLIs inherit pelhaim's environment, because they need their own auth. Check commands get a scrubbed environment from this allowlist: `PATH HOME USER LOGNAME SHELL LANG TERM TMPDIR CARGO_HOME RUSTUP_HOME`, every `LC_*`, and the project's `check_env`.
- **Process groups:** every child pelhaim spawns (CLI, check, git, gh, terminal opener) uses tokio `process` with `kill_on_drop(true)` and `process_group(0)`, so quitting pelhaim kills them all.
- **The exception:** a take-over terminal is deliberately spawned detached, so it outlives pelhaim.

## Review Focus

1. **pelhaim quits or crashes while trains run, then restarts.**
   - No orphaned `claude`/`codex` processes are left behind.
   - Stations that were Active or Checking come back Failed("interrupted by restart") with `[Retry station]`, and Retry follows the F32 table.
   - Restored trains re-claim their session keys, so observe never duplicates them.
   - No second worktree or branch is created.
   - Pinned in Task 8 (`restart_marks_active_stations_interrupted`, `restart_reclaims_sessions`) and Task 14 (`dropping_orchestrator_kills_children`).
2. **A worktree path or branch already exists, or the project root is dirty or not a git repo.** This covers a re-run, a leftover from a failed run, or the same minute giving the same train number.
   - pelhaim never reuses, forces or overwrites.
   - The station shows Failed with a reasoned `Failure`, and Retry picks the next free train number.
   - Pinned in Task 9 (`existing_branch_is_refused_not_forced`, `root_not_a_repo_fails_cleanly`) and Task 5 (`retry_after_worktree_failure_uses_next_number`).
3. **Signal look-alikes.** None of these may complete a station:
   - JSON in a code fence, or JSON mid-message;
   - a `step_complete` for another station;
   - two signal lines in one message;
   - malformed JSON;
   - an MCP `step_complete` with an unknown `station_id`;
   - a second completion in the same turn.

   Pinned in Task 11 (`signal_rejects_lookalikes`, `signal_two_objects_rejected`) and Task 6 (`step_complete_for_other_station_is_ignored`, `second_completion_in_turn_is_ignored`).
4. **Stale or repeated owner actions:**
   - approving revision 1 after an edit made revision 2;
   - signing off a rejected station that is running again;
   - approving a GitApproval from the Mac and the phone.

   The first valid answer wins, and push/PR runs exactly once. Pinned in Task 5 (`approving_superseded_revision_is_refused`) and Task 7 (`git_approval_runs_once`, `signoff_after_reject_is_refused`).
5. **Unusual git setups:** the base branch is `master`, there is no `origin`, `gh` is unauthenticated, or the push is rejected.
   - The base comes from `base_branch`.
   - A failure raises one `Failure` with the first stderr line, which never carries secrets.
   - The GitApproval goes back to the tray, retryable, and nothing retries on its own.
   - Pinned in Task 9 (`push_without_origin_reports_error`) and Task 7 (`push_failure_keeps_approval_retryable`).

Keyword and flag rules:
- **Matching:** case-insensitive whole words (ASCII boundaries) over `title + " " + detail`. Multi-word keywords match in sequence.
- **Mapping:**

  | Source | Flag |
  |---|---|
  | `design` field | `Decision` |
  | `security` field | `Security` |
  | design keyword | `Decision` |
  | security keyword | `Security` |
  | merge keyword | `Merge` |
  | prod keyword | `Prod` |

- **Override:** `keyword_override` suppresses only the keyword reasons.

Layout rules:
- **Columns:** the longest path from a root.
- **Chains:** a greedy path cover. Take the longest remaining path, breaking ties by plan order, then repeat.
- **Skipped steps:** left out.

Plan step state lives in the engine's own `plans` map, keyed by `(PlanId, step id)` (F7). It holds the status, train, branch, base, worktree, refs snapshot, attempts, session key, the Active intervals, and `base_moved`. A planned `Station` is only a view of that state. `fold` never removes a non-Done planned station; the display cap of `max_stations` applies to Done and observed stations first.

Behaviour:

**Planning**
- `PlanGoal` on a project with no `ProjectLaunch` (unconfigured, or no path) raises a `Failure` on DISPATCH. Its text is the Task 4 `launch_project` message (owner D). Otherwise it emits `Job::Plan`.
- `PlannerStarted { key }` claims `key` and its `/…` subagent keys, so their observe events are dropped (F23).
- Planners in flight add to the Dispatch `LineView.running`, and set that line `active` (F3). No train is created (owner A).

**Draft**
- `PlanDrafted` creates the `Plan` (Draft, revision 1), runs `apply_derived_flags`, then `validate`.
- It raises a `PlanReview` with `train: None`, `line: Dispatch`, and `errors` holding the Display strings.
- It adds one `Pending` station per non-skipped step to the project line's single track, with `plan: Some((id, step))`, titled with `step.title` and carrying `estimate_secs`. The stations are ordered by projected ETA, with ties broken by layout column and then plan order (owner F).
- If the line has no track yet, the engine creates it through the board change's line-train constructor, so a line with planned stations and no agents still shows.
- Draft stations are marked as drafts; they are drawn dim in Task 15.

**Review answers**

| Answer | Effect |
|---|---|
| `[0]` approve | `InvalidChoice` while `errors` is non-empty, or when the alert's revision ≠ the current revision. |
| `[1]` discard | The plan becomes Abandoned and its tracks are removed. |
| `Text(feedback)` | Same as `RevisePlan`, which emits `Job::Plan` with `revise`. |

- Approval sets `Approved` and `approved_at`, and writes a `Decision` row: title `Plan approved: <goal head>`, why `<n> steps, revision <r>`, `who: Owner`, the answer's origin, `source_alert`. It persists `DecisionLogged` (rule 2/4).
- An approved plan's planned stations stay on the project line, with their clocks, before any agent starts (owner F6 as amended by F).

**Edits**
- `EditPlan` emits `Job::EditPlan`.
- `PlanEdited` with `revision == current` bumps the revision by one, re-applies the derived flags, rebuilds the tracks, expires the old review and raises a new one.
- `PlanEditInvalid` raises a `Failure` listing `line N: message`.

**Scheduler** (after every fold)
- Free slots = `max_concurrent` − the plan stations in `Ready | Active | Checking` (F15).
- Take the next `Pending` station in plan order whose `effective_deps` are all `Done` or `Skipped`. `AwaitingSignoff` does not count as Done (§7.5).
- Mark it `Ready` and create its internal agent `Train` on the project line, folded into the line's single train (owner F):
  - session `SessionKey("pelhaim-plan:<id>/<step>-<n>")`, a synthetic key until `Launched`;
  - `Idle`, `train_number(now)` using the M1 collision rule;
  - `tag: Tagged(slug)`, `parent: None`;
  - a `SessionMeta` with `self_tag = Tagged(slug)` and `milestones = {step.title}` (F8, F11).
- Emit `Job::PrepareWorktree`:
  - `base` = `base_branch` for a root step, else the first effective dependency's branch;
  - `merge` = the other dependencies' branches.
- `WorktreeReady` sets the station `Active` (`started = now`, opening an Active interval) and the train's worktree, then emits `Job::Launch`.
- `WorktreeFailed` sets the station `Failed` and the train `Failed(reason)`, and raises a `Failure` with `[Retry station]`.

**Retry** (F32: the single table; Tasks 6 and 8 follow it)

| Station state at retry | Action |
|---|---|
| Conflict | `Job::RetryMerge` on the same worktree |
| Worktree and session exist | `Job::Launch { resume: Some(key) }` in the same worktree |
| Worktree exists, no session yet | Fresh `Job::Launch` in the same worktree |
| No worktree (WorktreeFailed, or Ready at restart) | Back to `Pending`, with the next free train number |

**`LaunchOne`**
- Builds a one-step plan:
  - step id `task`;
  - title = `truncate_chars(&title_from_prompt(prompt), MILESTONE_NAME_MAX)`;
  - detail = the prompt;
  - estimate = `estimate_secs` / 3600;
  - acceptance = the project's default check.
- Runs `apply_derived_flags` and `validate`. An invalid one-step plan raises a Failure.
- It is `Approved` at once, with the decision row `Launched one train: <title>`, why `pelhaim launch`.

**ETAs** (F30, owner C)
- `factor = correction_factor(&self.timings, Some(slug))`.
- An Active plan station gets `eta = started + estimate × factor`. That is M1's field, so `overdue` works unchanged.
- Every other station's projection uses `projected_finish`:
  - anchor = `max(now, approved_at)`, or `now` for drafts;
  - `fixed` holds Done steps at their actual finish and Active steps at `max(eta, now)`.
- `PlanView.etas` holds every step's clock. Pending/Ready plan stations also get `eta` set from it.
- `train.projected_arrival` = the clock of the last station on its plan's final column.

**Plan done:** a plan becomes `Done` when all of its non-skipped stations are `Done`.

**New states before Task 15:** until Task 15 draws them, the new states map to the nearest M1 colour:
- `Checking` → working;
- `DoneAwaitingSignoff` → wait;
- `Detached` → fork.

`CompactTrain.state` gains `"checking"`, `"signoff"` and `"detached"`. `compact()` ignores `plans`.

**Answers**

| Alert | Answer | Effect |
|---|---|---|
| launched `Question` | any | `Job::Send { text }` plus an automatic decision row (M1 title rules) |

**Signals**
- `Signal::StepComplete { station }` is accepted only while the train's plan station is `Active` (F43) **and** `station` equals its step id. Anything else is ignored and logged by id.
- `Signal::Ask` raises a `Question`.
- `Signal::Park` raises a non-blocking `ParkedDefault` plus a decision row `AgentDefaultUnconfirmed`, but only with `park_when_blocked`. Otherwise it is treated as `Ask`, with the default as option 1.

**Turn end and exit**
- `TurnEnded` with no accepted signal in the turn leaves the station Active and the train Idle, and raises `Stopped { can_send: true }`: "Train <n> stopped without declaring the step complete".
- `Exited { Some(0) }` with no completion does the same.
- Exits on Detached trains are ignored (F12).
- A non-zero exit or `None` sets the train `Failed("exit <code>")` or `Failed("killed")` and the station `Failed`, and raises a `Failure` with Retry.
- `OrchEvent::Stopped` (owner stop) raises no Stopped alert (F12). What else happens depends on `session_alive` (S9 ruling, 2026-11-25):
  - `session_alive: true`: the in-band interrupt ended the turn and the process still runs. The train becomes `Idle` with the label "stopped by owner" (paused), and the station stays `Active`. `SendToTrain` resumes it in the same session, and `TakeOver` and `[Mark complete]` stay available. No Retry is offered, because nothing failed.
  - `session_alive: false`: the SIGINT fallback fired, or the Codex exec process was killed with no resumable thread id. The train becomes `Failed("stopped by owner")` and the station `Failed`, with Retry. This is the pre-S9 behaviour.
- The `TurnEnded` rule above never sees an owner-interrupted turn, because the handle reports that turn as `Stopped` (Task 12).

**Sending and take-over**
- `SendToTrain` sends to a launched, non-Detached train. To an observed train it does nothing, and the M1 card stays.
- `TakeOver` emits `Job::TakeOver`.
- `TakenOver` sets the train `Detached` and unclaims the key, so later observe events fold into the same train. The runtime becomes `ObservedClaude { path }` / `ObservedCodex { path }`, from the stored path. Alerts on the train become `answerable: false`.
- An observe `TurnEnded` on a Detached plan agent raises `Stopped { can_send: false }`, answerable, with `[0]` Mark complete only (F13).

**Keep-awake:** `Checking` holds the Mac awake.

Behaviour (the §7.9 sequence):

**Checking**
- `step_complete` closes the station's Active interval and sets station and train to `Checking`.

**Check results** (`ChecksFinished` with a stale attempt is ignored)

| Result | Station | Train | Also |
|---|---|---|---|
| All pass, no sign-off needed | `Done` | `Done` | record the timing; run the scheduler |
| All pass, sign-off needed | `AwaitingSignoff` | `DoneAwaitingSignoff(id)` | raise a `Signoff` alert with the attempt, flags, summary, results, diffstat and manual texts |
| Any fail, attempts < max | `Active` | `Working` | open a new Active interval; send `"Checks failed (attempt <n> of <max>):\n<argv>: exit <code>\n<output_tail>"` per failed check |
| Any fail, at max | `Failed` | `Failed` | raise a `Failure` with Retry |

**Sign-off answers**
- `[0]` sign off: the station becomes `Done`, the timing is recorded, and a decision row `Signed off: <title>` is written.
- `Text(note)`: the station returns to `Active`, the train sends `"Owner rejected the step: <note>"`, and a decision row `Rejected: <title>` is written with why = the note.
- An alert whose `station`/`attempt` no longer matches an `AwaitingSignoff` station returns `InvalidChoice`.

**Base moved:** a rejected station whose dependants have already branched marks them `base_moved` (Q14). There is no automatic rebase.

**Git approval** (F16)

- Eligible chains emit `Job::FillPrs` with one `PrSpec` per station branch, bottom-up:
  - `base` = the station's own base;
  - `title` = `<project>: <step title>`;
  - `body` = the detail, the summary and the check list, ending in `🤖 Opened by pelhaim after owner approval.`
- `PrsFilled` raises the `GitApproval`.
- `[0]` approve emits `Job::PushAndOpenPrs` and writes a decision row `Approved PRs: <branches>`.
- `PrsOpened` raises a `Result` with the URLs and re-checks whether dependent chains are now eligible.
- `PushFailed` raises a `Failure`, and the GitApproval goes back to `Tray` and becomes answerable again. The answered state is reset for this kind only, which is what makes it retryable.

**Conflicts:** `MergeConflict` sets the station `Failed`, keeps the path, and raises a `MergeConflict` alert. There is no second track to join, so the board marks the conflicted station itself (Task 15):
- `[0]` emits `Job::RetryMerge { req, path }`;
- `[1]` emits `Job::OpenTerminal`.

**Releasable worktrees:** a station is `releasable` when no Pending or Active dependant still bases on its branch. The orchestrator uses this flag for `remove_worktrees`.

- **`shutdown(force)` (take-over, ruling 2026-11-25):** this fully releases the session before anything else may resume it.
  - Without `force`, it closes stdin, then waits up to `CLOSE_GRACE` (10 s) for the process to exit. With `force`, that step is skipped.

  - It returns only after the exit is confirmed. An already-exited process (e.g. an idle Codex train) returns at once.
  - The exit is reported neither as `Exited` nor as `Stopped`: `mark_closing_for_takeover()` was called first, so the orchestrator sends `TakenOver`. Closing stdin after a `result` exits 0 within about 1 s.

- The `Bash` tool's shell has no `~/.cargo/bin` on PATH on this machine, so agents fall back to absolute paths. This does not affect pelhaim's own check runner.
